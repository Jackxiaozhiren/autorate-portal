# V2 — The audience slice: sign in, ask a question, file the answer (2026-11-17)

One plan per slice, tasks at test-cycle size. Baseline: V1 closed at 348 tests, `serve` exists, an
offline packet replays to `612 /612`. This slice is about the people V1 could not serve: a P1/P2 who
does not run commands.

## 1. Decisions this slice is built on

| ID | Decision | Chosen | Why | Reversal |
|---|---|---|---|---|
| V2-D1 | Identity | Exchange an existing project token for a signed session cookie; no password storage | The token model already exists; adding passwords adds a credential store, reset flow and breach surface before anyone asked for it | A customer requires self-service accounts: add OIDC, not passwords |
| V2-D2 | CSRF | Double-submit cookie; session writes require `x-csrf-token`; token requests exempt | A cookie is ambient authority; a typed token is not | If the UI moves to token-per-request, the check becomes dead code and is deleted |
| V2-D3 | First screen | The claim question, not the certificate table | The table answers "what do we have"; the buyer asks "does this claim hold" | If five users cannot answer a claim in 90 s, restore the table |
| V2-D4 | Print | A4 stylesheet on the one renderer, shared by portal and self-contained document | An auditor files paper or PDF; a second template would drift | None expected |

## 2. Baseline

- 348 tests before this slice; 361 after T1–T3.
- The portal had a session *reader* and no issuer since M3: `read_session` was reachable only by a
  cookie nothing minted. T1 closes that dead path.

## 3. Tasks

### T1 — sign in (done)
1. `POST /api/v1/session` exchanges a project token for an 8-hour signed cookie naming the project.
2. The cookie carries the user's **email**, not the token's user id: the session reader resolves a
   person by email, and a cookie carrying an id fails every later request with "no such user". This
   was a real defect caught by the first test run, not a hypothetical.
3. Writes authenticated by the cookie require `x-csrf-token`; token-authenticated writes do not.
4. `DELETE /api/v1/session` clears both cookies and audits `session.revoked`.
5. Red tests: eight in `tests/test_session_login.py`, including a rejected token issuing no cookie
   and a session refusing another project.

### T2 — the question first (done)

2. Copy says, in both languages, that `cannot be bounded` is a result rather than a failure.
3. Red tests: `tests/test_first_screen.py` checks source order and both catalog entries.

### T3 — a sheet an auditor can file (done)

### T4 — external reader walkthrough (owner action, open)

walkthrough and record it; it cannot name the reader. Until then the gate stays open, and no test
can close it.

Build `annex_iv`, `iso_42001` and `aap` bundles from the real offline packet, confirm every line
names a source, and record which headings fall back to `no evidence published`. The code path exists
and is tested on fixtures; it has never been exercised on the real artefact set.

### T6 — a monitor that actually runs (done)
`monitor` is a CLI verb and the HTTP endpoint executes inline. T6 wires one external schedule (a
cron entry is enough) and records two consecutive observations, so `not-run` and `drift` are
distinguishable in the series rather than only in tests.

### T7 — login abuse controls (conditional)
There is no rate limit on `POST /api/v1/session`. A token is 32 bytes of entropy, so guessing is not
the threat; credential stuffing against a future password flow would be. T7 waits until V2-D1 is
reopened.

### T8 — a reload keeps the session (done)
`GET /api/v1/session` answers who the cookie names and returns the csrf value; the page resumes
before it offers a token field. Nine tests in `tests/test_session_resume.py`; browser readings and
the two defects found on the way are in §14.

## 4. Deliberately not in this slice

Password storage, self-service registration, OIDC, email delivery, per-user preferences, session
revocation lists, SSO. The session is stateless: a revoked membership takes effect on the next
request (the membership table is read every time), but a stolen cookie for an active member stays
valid until it expires. A revocation list is the fix if that becomes a requirement.

## 6. What T5 and T6 changed in the product

**`export` is now a command, not only an endpoint.** Without it the export drill could not be
run by anyone without a server, and F5 rule 4 promises a bundle a reader can re-hash alone.
`export build` and `export recheck` are the same `build_bundle`/`recheck` the endpoint calls.

**`build_bundle` no longer needs a database row.** It derived the digest and packet id from a
`db.Packet` row while both fields live on the manifest, so the CLI had nothing to pass. The
parameter is now optional; when a row *is* passed and disagrees with the manifest, the build
raises instead of picking a winner.

**`verdict_for` reads state before exit code, for two states.** The drill found that a genuine
`mismatch` was reported as `holds`: the portal computes the disagreement, so the process exits
0, and the old code trusted the exit code first. `mismatch → drift` and `refused` (no exit
code, or install sentinel 97) `→ refused` are now answered from the state. Every existing test
missed it because every one of them injected the tool's own exit 4, which the tool never emits
for this comparison.

**The monitor has a seventh verdict, `refused`.** A replay the portal stopped (integrity, pin,
platform, install) is not drift: nothing was observed, so the answer did not change. Calling it
drift would page an operator about a source that never moved — the failure mode T8 made likely
by turning platform mismatches into refusals.

Two exit-code collisions remain and are documented: `not_run` shares 3 with `not_certifiable`,
`refused` shares 4 with `drift`. Separating them means renumbering the tool's codes, which is a
protocol change.

## 8. What the visual walkthrough (2026-11-20) changed

The HTTP probe cannot see a page. A browser-agent pass over the same service (recorded in
`docs/verification/2026-11-18-v2-reader-gate.md`, Appendix A) executed the reader's clicks and
looked at the rendered result, and found two defects that no status code exposed. Both were
fixed on 2026-11-21; V2-B6 stays `not-run`, because neither fix answers whether a non-author
understands the verdict.

**Printing was unreadable under a dark system preference.** The page legitimately follows
`prefers-color-scheme` on screen, but the print block inherited it: with dark set, the computed
print colours were `color: rgb(255,255,255)` on a dark canvas, so the filed A4 sheet would have
carried white text on white paper. `@media print` now pins `color-scheme: light`, sets
`html, body { background:#fff; color:#000 }`, darkens `.muted`/`.triple` for paper, and drops the
hover tint. The self-contained document already pinned light colours and is unchanged.

**A validation error was the one English sentence on a Chinese screen.** `Claim.from_dict`
raised `ClaimError` with a fixed English message and the HTTP layer passed `str(exc)` through as
the 422 `detail`. `ClaimError` now carries the missing field names as data and exposes
`localized(locale)`; the message and the list separator are catalog entries
(`error.claim_incomplete`, `punct.list_separator`), and field names reuse the existing
`label.share|field|unit|population`. `str(exc)` remains English, so the CLI and locale-less token
API keep their wording.

Two regression tests were added — the print block must opt out of a dark preference, and the 422
must answer in the locale it was asked in. After both fixes: full suite **376 passed, 1 warning**;
the 11-step probe is unchanged (`failures: None`).

## 10. The boot step took no lock (2026-11-22, later the same day)

The image applied the chain with `alembic upgrade head`. One container made that look sufficient;
it is a race the moment there are two. Four processes on one empty PostgreSQL database under the
old command: **one exited 0, three exited 1** on `duplicate key value violates unique constraint
"pg_type_typname_nsp_index"` — they all tried to create `alembic_version` at the same time. The
same four through the new command: **four exit 0**, one revision. SQLite fails the same way
(`table alembic_version already exists`) and is closed by a file lock; three image replicas on one
empty database all reached `healthz 200` in 4 s.

`autorate-portal migrate` is now the only path that upgrades a database. It holds a schema lock
for the length of the chain — `pg_advisory_lock` on a key derived from `current_database()`, or
`flock` on `<database>.migrate.lock` — waits `AUTHORATE_MIGRATE_LOCK_TIMEOUT` (default 120 s) and
then refuses with exit 4 rather than starting against an unknown schema. A dialect with no lock is
refused outright: an unlocked upgrade is not a slower upgrade, it is the race.

Two paths, one lock. A deployment that prefers a migration job sets `AUTHORATE_MIGRATE_ON_START=0`
on the replicas and runs `autorate-portal migrate` in the job. That flag is a contract, not a
convenience: on an unmigrated database the replica still answers `healthz 200` and only fails at
the first request that reads a table (measured: 500 on `POST /api/v1/session`). Nothing in the
image detects the wrong order, so the job must be sequenced before the replicas.

Readings in `docs/verification/2026-11-22-postgres-and-container.md` §P9-P15. Two definitions that
were wrong and are now pinned by tests: the image must call the locked command and never bare
`alembic` (`tests/test_serve.py`, `tests/test_dockerfile.py`), and `/healthz` is a liveness check
that does not prove the schema exists.

**The probes were then split (18:42-18:49), because naming a gap is not closing it.** `/healthz`
stays a constant and stays the container's `HEALTHCHECK`. `/readyz` is the gate an orchestrator
should use: one connection, `SELECT 1`, and the revision in `alembic_version` against the head this
build's chain ends at. It answers 200 `{"status":"ready","schema":…}` or 503 with
`database-unreachable`, `schema-missing`, `schema-behind` (naming `applied` and `expected`) or
`schema-unverified`. Measured on the rebuilt image against PostgreSQL: a skipping replica with no
job is `healthz 200 / readyz 503 schema-missing` (§P17, which is §P15 closed); the job path is
ready; a live replica flips to `schema-behind` after a `downgrade` and back after `upgrade` without
a restart; and `docker stop` on the database leaves `/healthz` 200 and the container `(healthy)`
while `/readyz` reports `database-unreachable` (§P16-P20).

The body never carries a driver message, because a probe is unauthenticated and a driver's message
quotes the connection URL — asserted with a password-bearing URL in `tests/test_readiness.py`. The
chain now travels inside the wheel (`force-include`), so `schema-unverified` is what a build
without migrations says, not what a normal install says.

## 11. The suite could only see one dialect (2026-11-22, 19:05-19:35)

Every migration test in the suite runs on SQLite, which is the right default: no service, no
credentials, a few seconds. The cost surfaced once the chain had a constraint to change. `0005`
drops and re-creates `ck_artifact_kind`; PostgreSQL does that in place, SQLite can only rebuild
`artifact` into `_alembic_tmp_artifact`, copy the rows and rename. P1-P4 and P9-P20 exercised the
PostgreSQL path by hand, and nothing in the repository would have noticed a later migration that
compiled for SQLite and not for the database the image ships against.

`tests/test_migrate_offline.py` closes that with Alembic's offline mode, which renders the chain
for a dialect without connecting to anything. It asserts that every revision is stamped in chain
order, that PostgreSQL emits `ALTER TABLE artifact DROP CONSTRAINT` / `ADD CONSTRAINT` and no
temporary table, that SQLite emits the rebuild and never `DROP CONSTRAINT`, that both carry the
same six kinds, and that rendering a SQLite URL creates no file while the PostgreSQL URL points at
TEST-NET-1. Replacing `batch_alter_table` with `op.drop_constraint` in `0005` turned four SQLite
assertions red and left the PostgreSQL ones green, so the test separates the dialects rather than
accepting whatever they emit.

This is not execution. Rendering proves the statements are the ones this build would send and that
they describe the intended end state; it does not prove a server accepts them, and it says nothing
about the lock. That evidence stays where it was made, by hand on one node, in
`docs/verification/2026-11-22-postgres-and-container.md`.

## 12. The rendering needed a server (2026-11-22, 19:45-20:10)

§11 closed the compile-time gap and said plainly what it left open: rendering is not execution.
The evidence for execution was P1-P20, made by hand on one node, and a later change to a migration
or to the lock could have broken PostgreSQL without turning anything red.

CI now supplies the server. A `postgres` job starts `postgres:17`, installs `.[postgres]`, and runs
`tests/test_migrate_postgres.py` together with the migration and readiness files: 26 tests, 0
skipped, 3.9 s. The new file covers what only a server can answer — the chain is accepted and
`ck_artifact_kind` gains `wheel`; four replicas started together all reach the head with one
`alembic_version` row; a held `pg_advisory_lock` becomes `MigrationLockTimeout` in about half a
second **with no table created**; the lock is free afterwards; a downgrade to `0004` removes
`wheel` and an upgrade puts it back; `/readyz` answers `schema-missing` on an unmigrated server and
`schema-behind` after a downgrade, naming both revisions.

The file skips when `AUTHORATE_TEST_PG_URL` is unset, so the default suite still runs with no
service — 411 passed, 7 skipped. That tolerance is exactly how a job turns green while testing
nothing, so the job reads pytest's summary and exits 1 if `N skipped` appears. Verified both ways
locally: with the variable set, 26 passed and the guard is silent; unset, `7 skipped` and the guard
fires.

Removing the lock from `_postgres_lock` makes the held-lock test fail in 0.7 s and makes the
four-replica test hang on PostgreSQL's own DDL lock — the defect from §10, observed from the other
side. The first mutation attempt had to be killed at the tool's limit for that reason.

Still not proven: failover, TLS, a managed cluster, more than one tenant, and an orchestrator that
acts on `/readyz`. The job executes the contract; scheduling remains the deployment's job.

## 13. The container readings became a job (2026-11-22, 20:30-21:20)

P12 and P16-P20 were the strongest evidence in this repository and the least repeatable: two
containers, `curl`, and a person deciding the answer looked right. Every one of those readings
depends on the Dockerfile, the probe router and the migration command — three files that change.

A `container` job now builds `autorate-portal:ci` and runs `tests/test_container_replay.py`, which
repeats the readings: a skipping replica is alive and `schema-missing`; a one-shot migration job
makes the replica that was **already running** ready, with `StartedAt` unchanged; three boot-time
replicas leave one `alembic_version` row; stopping the database leaves `/healthz` 200 and
`/readyz` `database-unreachable`, and starting it restores readiness without a restart; the process
is uid 10001. Five tests, 10.5 s on this machine.

The image mutation is what makes it a test rather than a transcript: change the command from
`migrate --if-enabled` to `migrate`, and the skipping replica migrates at boot — readyz 200 — so
P17's assertion fails in 2.6 s on the rebuilt image.

Writing it produced two lessons worth keeping. Docker publishes the port before the server listens
and closes the connection without a response, so a poll that only catches `URLError` is flaky by
construction. And the official `postgres` image answers `pg_isready` from a bootstrap server it
then shuts down, so CI's first test died on `FATAL: the database system is shutting down` after the
same file had passed locally; the fixture now counts `ready to accept connections` banners (two on a
fresh container) and confirms with a query. Reproduced: `pg_isready` 0 then `psql` rc=2, versus rc=0
after the banner wait.

What it still is not: an orchestrator. The test drives the probes; Kubernetes does not. One host,
one database, no failover, no rolling update under traffic.

## 14. The reload forgot a session the cookie still held (2026-11-22, 21:45-22:40)

The decisions promised "sign in once, for eight hours". The page could not keep that promise with
the server it had: the cookie survived a reload, but no route said whose it was, and the csrf value
lived only in the script's memory. Reproduced against a real app before changing anything — after a
login, a client holding only the cookies read `/api/v1/certificates` with **200** and had no route
to ask who it was (**404**), so every write after a reload answered **403**
(`a session-authenticated write needs the csrf token`) and the reader was shown a token field for a
token the cookie already carried.

`GET /api/v1/session` closes it. Cookie only, because a token caller has no session to resume and
answering with an identity that did not come from a cookie would blur the two credential types the
write rule keeps apart. It returns the actor, role, project and the double-submit value; when only
the csrf cookie is gone it re-issues one, because the session it belongs to is still valid; it sends
`Cache-Control: no-store`, because an answer that depends on a cookie must not be served to the next
reader by a cache that ignores one. The page asks on load, before it offers a token field, and hides
that field once it knows who it is.

Two defects turned up on the way, neither of which a source assertion would have found:

1. Switching to 简体中文 re-rendered every `data-i18n` node and left the identity line in English.
   The line carries two values, so it cannot use `data-i18n`; a language switch now rebuilds it.
2. A member whose membership was gone got a **500** from every route the cookie touched.
   `principal_for_project` raises `Forbidden`, which is not an `AuthError`, and `principal` caught
   only the latter. It is a **403** now — what the class documents — and the new route answers the
   same way, so one session gets one answer.

A third reading came from the same pass: with `load()` finally running at startup, an empty project
greeted the reader with "no certificates in this project yet" in the red alert slot. That is a
state, not a failure, and it now has its own muted line.

Evidence: `tests/test_session_resume.py`, nine tests — a fresh client carrying only the cookies
resumes with the same identity and csrf; the resumed csrf is accepted by a write; no cookie is 401
and issues nothing; an expired cookie is not an identity; a revoked membership is 403 rather than
500; a lost csrf cookie is reissued and usable; the answer is `no-store`. Disabling the re-issue
branch fails exactly one of them. In a browser against a local service: signing in hides the token
field and names `producer@example.test · project prj-1`; a reload keeps both; **Check a claim** after
the reload returns `cannot_be_bounded` instead of 403; switching to 简体中文 prints
`已登录：producer@example.test · 项目 prj-1`; signing out and reloading brings the token field back.

Not proven: a stolen cookie is still valid until it expires (section 4's deferral stands; this adds
no revocation list), and the language choice still resets on reload because it lives in the page and
not in the session.

Suite after this change: **420 passed, 12 skipped**; `ruff` clean on the CI rule set.

## 15. The export was readable and unfilable (2026-11-22, 23:45-00:30)

The bundle endpoint has always returned bytes: a canonical payload, a `x-bundle-sha256` header, and
`export recheck` to confirm the file alone. The page did the one thing that makes all of that
useless to the reader it was written for — it parsed the response, re-serialised it with
`JSON.stringify(body, null, 2)`, and printed it into a `<pre>`. A P1 could read the bundle and could
not file it. Worse, the thing on screen was a **second encoding** of the bundle: reformatted JSON
that no hash in the system described.

`buildExport` now saves the response as a blob, so the bytes on disk are the bytes the server sent.
The file is named `kind-<first 12 hex>.json`, the full `x-bundle-sha256` is printed beside the link,
and the document stays readable in a collapsed `<details>` instead of taking over the page. The 409
path is unchanged in kind but now legible: `call()` carries `status` and `body` on its error, so a
blocked export prints `block_reason` — the sentence — instead of "409 Conflict".

Two defects came out of doing it in a browser, and neither is visible to a source assertion:

1. The export line, its link and the `preview` summary are built when the bundle arrives, so they
   cannot carry `data-i18n`. Switching to 简体中文 translated every button around them and left them
   in English — the identity line's defect from section 14, one element over. `state.exported` now
   keeps what was rendered and `applyMessages` rebuilds it.
2. `shareable badge` had never been translated at all: no `data-i18n`, no catalog entry. It has both
   now (`label.badge` / `分享徽章`).

Evidence. `tests/test_export_download.py`, eight tests: the page asks for a blob and not JSON, the
old writer is gone, the name carries twelve hex characters and `.json`, the object URL is released,
`block_reason` is read, the catalog carries the three new strings with their placeholders in both
languages, the line is rebuilt on a language switch, and the badge is translated. Four of these
return 0 against `HEAD~`, so they are not describing code that already existed.

In a browser, against a local service with a seeded project and an uploaded packet:
signing in as a compliance member and pressing **export** dropped
`annex_iv-d8edc57d9b29.json`, **1992 bytes**, into the download folder; `cmp` against the bytes the
API returned is identical (both `f897b172…`); the twelve characters in the name are the first twelve
of the response header; and `export recheck` on the **downloaded file** printed `ok`, exit 0. In
简体中文 the line reads `1992 字节`, the link `保存审计包`, the summary `预览`; switching back to
English rebuilds all three without re-exporting. Moving the packet out of the store and pressing
export again printed `the packet store cannot produce this bundle` in the alert slot, not a status
code.

What this does not prove: that a download works in every browser. This pass used the embedded
browser only, and it silently **overwrote** the earlier file of the same name rather than appending
a suffix, so a reader who exports twice keeps one file. Firefox and Safari were not tried. The
`x-bundle-sha256` is still a payload hash, not a file hash — the README now says so plainly, because
`shasum` on the file will never match it and the only correct check is `export recheck`.

Suite after this change: **428 passed, 12 skipped**; `ruff` clean on the CI rule set.

## 16. The runbook could not be followed from a clean machine (2026-11-23, 16:26-16:52)

could do is read its own runbook as a stranger would, and the runbook did not survive that. Step 1
issued tokens for `u-ada` and `u-lin`; nothing in the document created those users, the org, the
project or the store, and nothing ingested the packet. On a clean machine the old text therefore
produced a token that answered

```
POST /api/v1/session -> 401 {"detail":"the token was not accepted"}
```

measured against a freshly migrated database. The predecessor of that instruction had been run once,
by hand, on a database that already had the rows — so the gap was invisible in the only place it was
ever executed.

`tools/walkthrough.py` is that missing step. `up` builds the M4 demo packet **through
`tests/conftest.py`**, migrates a fresh database through the chain, ingests, issues one token per
reader and prints the serve command, the LAN address and two cards. `check` then signs in the way a
reader does — token in, cookie and csrf out — and asserts the ten readings the runbook promises.

Three things came out of building it, and the first one is the reason to trust the other two:

1. The first draft seeded with `db.create_all`. The database worked and `/readyz` answered
   `503 schema-missing` — every table, no `alembic_version` row. A walkthrough database that teaches
   the facilitator to ignore the one probe built to be trusted is worse than no probe. Seeding now
   goes through `migrate.upgrade_to_head`, and `test_the_seeded_database_answers_ready` fails if it
   ever goes back.
2. The preflight had to be shown able to fail. On a migrated, never-ingested database **only** the
   `certificates` line turns red; Q1–Q3 answer `cannot_be_bounded` exactly as they do on a measured
   project. `cannot_be_bounded` is the right answer both to "this pack never measured the field" and
   to "this project has no evidence", so the count is the only line that separates a facilitator who
   skipped the ingest from a project that is genuinely empty. That is now a test that asserts the
   failing set is exactly `["P1 certificates", "P2 certificates"]`.
3. A token signed with a different salt, a missing key in `tokens.json`, and a port where nothing
   listens each fail on their own line with a sentence rather than a traceback (`nothing answered at
   … start the service first, or pass --base`).

The packet is compared byte for byte with the `m4_built` fixture
(`sha256 5a17d2486df41841758cbcb627df89489530f93061a74c3368fc9d66d6131f8e`, 34 entries, 33 artefacts,
7 certificate summaries, all `feasible = 0`), so the readings in the runbook describe the file the
suite asserts against. Two builds produce the same hash, so a lost tarball is re-issued, not
reconstructed.

The runbook's step 1 now calls the tool. The manual path survives as an appendix and was executed
**verbatim from the document** — extracted block, `indexed True`, two tokens, `/readyz` `ready`, the
same ten `ok` lines — because an appendix nobody runs is a paragraph, not an instruction. It says
what it cannot replace: the packet still comes from `walkthrough.py packet`.

Evidence: `docs/verification/2026-11-23-v2-walkthrough-pack.md`; `tests/test_walkthrough.py`, ten
tests, with three mutations that turn them red (`create_all`, `CERTIFICATES = 8`, and dropping the
row-count comparison).

What this does not prove: anything about the readers. The 90-second judgement, the wording people
actually stumble on, and whether `cannot_be_bounded` reads as a result rather than a failure are all
still unmeasured, and the print checks stay manual. V2-B6 stays `not-run`; T4 is prepared, not closed.
